# signal-forge

- Real data lives on prod: `ssh vm106`, container `signal-forge-app-1`, db `/app/data/app.db`. Local `data/app.db` is a stale copy — never answer from it. Use the `prod` skill.
- Start with `bun run prod guide` — it lists every command there is. `sql "<query>"` (read-only), `schema`, `snapshot <source>` answer most questions. A new command is one entry in `src/operations/`, never a script on the host.
- Open a session with `bun run prod issues`, `bun run prod silent-sources` and `bun run prod flaky` — three different kinds of broken, and each is invisible to the other two. `issues` reads the present, `silent-sources` reads absence, `flaky` reads the failure rate. A source failing two attempts in three and succeeding on the third is never silent and only red if you look in that minute: `arena` sat at 73% for three days, carrying the codenames, and nothing said so.
- Ask the reports before the tables. `sources` keeps a row for every source that ever ran, including retired ones: the four designarena boards frozen at 2026-09-09 were pruned by 7f59f35 the next day, and their row is the date they stopped being asked, not a fault. The reports filter by the registry; raw SQL does not, and a stale row read straight out of the table looks exactly like a broken collector.
- The same is true of channels, and it is easier to get wrong because the registry is a config file rather than a table. `bun run prod destinations`, never `deliveries` grouped by `destination_id`: that grouping returned eight channels on 2026-09-24 and three are configured, which turned five retirements into a finding about missing delivery records. If the report marks a channel retired that sent something yesterday, it says so — that means the config being read is not the one doing the sending.
- `bun run prod usage` says which commands are actually used and, from the journal of raw `sql` calls, which question has been asked by hand often enough to deserve a command. Every call on every surface is journalled now, reads included; `journal` still shows only the ones that changed something.
- Any command takes `--tsv` and it already works through `prod`. It existed for weeks before anyone used it; reach for it before hand-parsing JSON out of a terminal.
- Before changing a projection — Model Facts, hypotheses, stories — run `bun run rehearse-projections [events]`. It rebuilds in full on a copy of prod, then checks two things the gate cannot: that an incremental update of every source changes nothing, and that revealing the newest events one at a time lands on the same bytes as a full rebuild. Both caught real bugs the 725 tests passed straight through — an ordering mistake from `localeCompare` where SQLite means BINARY, and a staleness that predated the change. An incremental projection that is merely close corrupts derived data slowly and silently.
- Before changing what reaches a reader, run `bun run rehearse [days] [destination]`. It copies the live database and judges the same real events twice — once by the policy at `--base` (HEAD by default) and once by this working tree — then prints every decision that moved. Replaying the three rules shipped on 2026-09-24 named exactly the three cards they were written for and nothing else. Measure there, not in the channel.
- Work on main, Deploy is a push: `git push`, find the run by head SHA, `gh run watch --exit-status`, then `bun run prod verify <symbol>` — it checks the schema version, the hot-path indexes, the failures since the restart and that symbol in `/app/dist`, which is the only one of them that can tell a new image from an old one still running.
- A new index is not a used index. 049 shipped five and the planner ignored every one of them until `ANALYZE` populated `sqlite_stat1`; from outside, an unused index and a missing one look identical. Ship `ANALYZE;` in the same migration and confirm with `EXPLAIN QUERY PLAN` against a copy of prod (`.rehearsal/prod.db`, left behind by `rehearse`).
