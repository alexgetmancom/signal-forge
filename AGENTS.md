# signal-forge

- Real data lives on prod: `ssh vm106`, container `signal-forge-app-1`, db `/app/data/app.db`. Local `data/app.db` is a stale copy — never answer from it. Use the `prod` skill.
- Start with `bun run prod guide` — it lists every command there is. `sql "<query>"` (read-only), `schema`, `snapshot <source>` answer most questions. A new command is one entry in `src/operations/`, never a script on the host.
- Open a session with `bun run prod broken`. It asks all four readings at once — `issues` the present, `silent-sources` an absence, `flaky` the rate, `outages` the correlation — and each is blind to the other three: a source failing two attempts in three and succeeding on the third is never silent and only red if you look in that minute, which is how `arena` sat at 73% for three days carrying the codenames. Read `readings` first; a source two of them agree on is the one to open. The four still answer on their own when the question is already narrow.
- Read `flaky` by `faultRate`, not `failureRate`, and ask `bun run prod failures <source>` next. A failure carries a kind now (`src/failure.ts`), so a `degraded` row — this service's own shrink guard refusing a short answer — is counted and named separately from a collector that cannot read the page: 73 of `arena`'s 103 failures were the guard, and one rate called that 58% broken. `failures` prints the structure of each complaint, which for a schema failure is the field paths the parse objected to. No upstream value is ever stored, which is why the body of a failed parse is not.
- Several sources going flaky at once is usually one host. `bun run prod outages` groups failures by the pacing group the sources share -- which is a host name, because that is why the group exists -- and counts the minutes in which more than one of them failed, since independent failures do not land in the same minute. The five `artificial-analysis` sources logged 53 `ECONNRESET` in seven days at ten per cent each: five entries in `flaky`, one upstream.
- `bun run prod timings --name pipeline --limit 5` is what this service spends its time in, with p50 and p95. It was called `code_analytics` and lived in the `sources` section, and ten raw `sql` queries were written against `code_metrics` by hand rather than found -- a command nobody can find and a command that does not exist look identical from the outside, and only one of them is fixed by writing code. `usage` now names the command that already answers a hand-written query, which is the cheaper half of that problem.
- A successful answer leaves a shape behind: `bun run prod failures <source>` prints `shapes` (the paths, the types, and how many entries each array held) and `shapeChange` between the two most recent. Paths and types only -- no upstream value is stored anywhere, here or in failure evidence. This is the thing that did not exist when `arena` broke: the diagnosis needed a live fetch of the page, and "the response changed" could only be a guess. A roster of 61 and one of 1083 are the same shape, so the sizes are kept beside it as a range rather than as a new contract.
- Ask the reports before the tables. `sources` keeps a row for every source that ever ran, including retired ones -- eight on production, among them the four designarena boards frozen at 2026-09-09 and pruned by 7f59f35 the next day. Their row is the date they stopped being asked, not a fault. This is now enforced rather than remembered: `check-sql` fails the gate on any SELECT in `src/` that reads `sources` as a list without the registry (a lookup keyed on `sources.id` is fine, since an event from a retired source still came from it). It caught `release.ts`, which folded retired rows into the count that says whether a deploy is healthy. `failures <source>` answers `registered: false` for a name the registry no longer asks for.
- The same is true of channels, and it is easier to get wrong because the registry is a config file rather than a table. `bun run prod destinations`, never `deliveries` grouped by `destination_id`: that grouping returned eight channels on 2026-09-24 and three are configured, which turned five retirements into a finding about missing delivery records. If the report marks a channel retired that sent something yesterday, it says so — that means the config being read is not the one doing the sending.
- `bun run prod usage` says which commands are actually used and, from the journal of raw `sql` calls, which question has been asked by hand often enough to deserve a command. Every call on every surface is journalled now, reads included; `journal` still shows only the ones that changed something.
- Any field a command accepts can be given as `--field value`, `--field=value` or `--min-confidence` for `minConfidence`; positions still work for the common ones. Ask `guide` for what a command takes, because the usage line only lists the positional ones: `suppressions --destinationId`, `stories --since --vendor`, `journal --operation` and `guide --all` are all real and none of them appears there.
- Any command takes `--tsv` and it already works through `prod`. It existed for weeks before anyone used it; reach for it before hand-parsing JSON out of a terminal.
- Before changing a projection — Model Facts, hypotheses, stories — run `bun run rehearse-projections [events]`. It rebuilds in full on a copy of prod, then checks two things the gate cannot: that an incremental update of every source and every story changes nothing, and that revealing the newest events one at a time lands on the same bytes as a full rebuild. Model Facts and hypotheses are compared together, because they are updated together from the same dirty set. Three real bugs so far that the tests passed straight through — an ordering mistake from `localeCompare` where SQLite means BINARY, a staleness that predated the change, and an incomplete dirty set. An incremental projection that is merely close corrupts derived data slowly and silently.
- A failure's sentence is trusted because of its type, never because of its first word. Throw `SourceError(kind, message)` from a collector and the message is stored and printed; throw a bare `Error` and it is described instead (`unexplainedFailure`). The rule this replaced was a regex on the message, which both lost the diagnosis of any new wording and would have published an upstream response body that happened to start with the word `Source`.
- Reach for `tests/fixtures/build.ts` before writing an INSERT in a test. `anEvent`, `aSnapshot`, `anAttempt` and `aCall` produce rows that satisfy the CHECK constraints -- `authority`, `confidence`, `evidence_type`, the ISO-8601 shape of every `_at`, and the snapshot an event has to point at. Writing those by hand produced `CHECK constraint failed` instead of a test five times over two sessions.
- Before changing what reaches a reader, run `bun run rehearse [days] [destination]`. It copies the live database and replays the same real events twice — once at `--base` (HEAD by default), once in this working tree — in two halves, because "what reaches a reader" is two questions. The policy replay prints every delivery decision that moved; the card replay renders every event at both detail levels and prints every card whose text moved. Replaying the three rules shipped on 2026-09-24 named exactly the three cards they were written for; renaming one sentence in `shape.ts` moved 90 cards, because `eventEmbed` suppresses that sentence by matching its first two words. Measure there, not in the channel.
- Work on main, Deploy is a push: `git push`, find the run by head SHA, `gh run watch --exit-status`, then `bun run prod verify <symbol>` — it checks the schema version, the hot-path indexes, the failures since the restart and that symbol in `/app/dist`, which is the only one of them that can tell a new image from an old one still running.
- `timings` measures a window, and after a deploy the window is `--since boot` (also an ISO instant, or `90m`/`6h`/`2d`). Buckets are hourly, so a release at 13:34 leaves the 13:00 bucket describing both builds: `--since` reports that hour in `straddled` and leaves it out rather than averaging the old build into the new one. `days` then says what was actually covered.
- Before deleting or retiring rows of anything, ask `bun run prod references <table>` (`events` by default). It reads the foreign key graph out of the running database: which references cascade, which clear themselves, which `refuse` -- those are the entire job -- how many rows are already orphaned, and the order a delete has to take. Thirteen keys point at `events` and that is usually given as the reason retention was never written; six cascade, two clear, and six refuse. Measured 2026-09-25 on 377MB of production: zero orphans anywhere, so the constraints describe the data and not only the intention.
- A column name in a SQL string is not checked by the compiler, and `bun run check-sql` is what checks it: it builds the schema from the migrations in memory and asks SQLite to prepare all 436 statements in `src/` and `scripts/`, so `operator_journal.at`, `source_collection_metrics.ok` and `total_ms` fail the gate instead of returning an empty report on prod. A statement it cannot parse is one assembled from interpolated fragments and is counted, not reported. `tests/` is deliberately out: the names written wrong there are written wrong on purpose, and a test with a real typo fails the second it runs.
- A new index ships with the read it was for, in src/storage/hotQueries.ts. `rehearse-migration` runs `EXPLAIN QUERY PLAN` for each of them before and after, prints what moved, and fails the rehearsal on a read that was a SEARCH and came back a SCAN. A test asserts every one of them uses an index on a fresh schema, so an index removed and a read nobody indexed both break something.
- A new index is not a used index. 049 shipped five and the planner ignored every one of them until `ANALYZE` populated `sqlite_stat1`; from outside, an unused index and a missing one look identical. Ship `ANALYZE;` in the same migration and confirm with `EXPLAIN QUERY PLAN` against a copy of prod (`.rehearsal/prod.db`, left behind by `rehearse`).
